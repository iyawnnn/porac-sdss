# Database Reference

> **Update this document whenever a migration adds, removes, renames, or significantly changes a table, view, enum, or important column.** A schema change without a matching update here is an incomplete change.

This is a plain-English reference for every table/view PORAC-SDSS's Postgres database holds — what it's for, who touches it, and whether an empty table means something is broken or is just normal. It exists because a database audit found several real, correctly-designed tables that were easy to mistake for dead schema just by glancing at row counts in a fresh development database.

Two ORMs are in play (see `CLAUDE.md`'s Architecture section for the full rationale): Drizzle (`api/src/db/schema.ts`) manages every non-geometry column; anything touching a `geometry` column goes through the raw `PG` postgres.js client instead, so several tables below exist in Postgres but are intentionally **not** in `schema.ts`.

---

## A. Core application tables

### `citizens`
- **Purpose:** One row per citizen account. Email/password login, or OAuth-only (nullable `password_hash`).
- **Reads:** Auth (`AuthService.citizenLogin`), report submission (attaches `citizen_id`), Account & Security page, admin views that show reporter identity.
- **Writes:** Signup (`AuthService.citizenSignup`), OAuth first-login, password change/reset (`password_changed_at`, `session_valid_after`).
- **Expected empty?** No in any environment with real usage; empty only immediately after a fresh migration with no seed run.
- **Ownership:** Application (Drizzle).
- **Never manually delete:** Not a system table, but deleting rows here breaks every FK'd `reports`/`password_reset_tokens`/`citizen_identities`/`citizen_audit_events` row — treat deletions as a real data-loss operation, not routine cleanup.

### `admins`
- **Purpose:** One row per admin/staff account. Carries its own session-security columns, parallel to `citizens`': `password_changed_at`, `session_valid_after` (bumped on password change/reset, checked by `SessionService.verifyAdminSession` to invalidate stale JWTs server-side), and `is_active` (admin deactivation — see §E).
- **Account fields (Appendix H ADMINS; manuscript revision Phase 2, step 2e, migration `0039_staff_account_types.sql`):** `account_type` (`admin_account_type`: `PERSONNEL` | `SYSTEM_ADMIN`), `office` (`MEO` | `MDRRMO` | NULL) and `is_focal` (boolean). Both new columns are `NOT NULL` with **no default** — the app always sets them. These three decide every access check (`isSystemAdmin` / `isFocalPersonnel` / `isOperationalPersonnel` in `api/src/common/authz/admin-scope.ts`, mirrored in `lib/utils/adminScope.ts`):
  - **System Administrator** — `SYSTEM_ADMIN`, no office, not Focal: account administration only, no operational access.
  - **Personnel** — `PERSONNEL`, an office, not Focal: office-scoped operational staff.
  - **Focal Personnel** — `PERSONNEL`, office `MDRRMO`, `is_focal = true`: intake/screening only. Its MDRRMO office grants **no** operational access (no MDRRMO queue or office scope, no Work Orders, no assessments).
  - **CHECK `admins_account_type_office_focal_check`:** `(account_type = 'SYSTEM_ADMIN' AND office IS NULL AND is_focal = false) OR (account_type = 'PERSONNEL' AND office IS NOT NULL AND (is_focal = false OR office = 'MDRRMO'))`. `AdminsService` enforces the same rule first, with clear 400s.
  - **Mapping from the old `role` (0039 backfill):** `officer` and `supervisor` → Personnel with the same office (they had identical permissions everywhere); `focal` → Focal Personnel on MDRRMO (a focal with no office was moved to MDRRMO); `system_admin` → System Administrator. A guard stops the whole migration with counts, changing nothing, if an officer/supervisor has no office, a focal is on MEO, or a system_admin has an office. The same UPDATE sets `session_valid_after = now()`, so **every staff member is logged out once**; a re-run maps 0 rows and logs nobody out again. `0039_staff_account_types.check.sql` reports admins by (role, account type, Focal, office), mapping mismatches and CHECK violations (must be 0), and audit events by (actor_role, actor_account_type). Run with `pnpm --prefix api migrate:staff-account-types`.
- **`role` (kept until Phase 8):** still `NOT NULL`, but only a **sync mirror** — nothing may read it for access, the session doesn't carry it, and the API never returns it. Create/update write it: Focal Personnel → `focal`, System Administrator → `system_admin`, other Personnel keep an existing `officer`/`supervisor` value, else `officer`. Dropped in Phase 8.
- **Reads:** Admin login/session verification, Admin Management page, every RBAC/office-scope check (`api/src/common/authz/admin-scope.ts`, reading the session's `accountType`/`isFocal`/`office`), the Focal intake notification fan-out (`account_type = 'PERSONNEL' AND is_focal`).
- **Writes:** `seed:admin`/`seed:e2e-admins` scripts, Admin Management create/update/deactivate/reactivate, password reset. Code from before step 2e can't create an admin against a migrated database (no `account_type`), but still logs in and works otherwise.
- **Expected empty?** No — at least one `system_admin` must exist for the app to be operable; the last-active-system-admin lockout (`AdminsService`) exists specifically to prevent this table reaching a state with zero active system admins.
- **Ownership:** Application (Drizzle).

### `reports`
- **Purpose:** One row per citizen submission (photo, EXIF data, location, citizen-selected severity, moderation flags). Each new report creates its own `tickets` row (automatic `ST_DWithin` merging was removed in manuscript revision Phase 1, step 3; older tickets may still carry several reports) — see CLAUDE.md's "Report → Ticket separation."
- **Reads:** Ticket detail page (member reports), `/admin/flagged` moderation queue, dedup/merge logic.
- **Writes:** Citizen report submission (`ReportsService`), moderation actions (`moderation_status`/`moderation_note`/`moderated_at`/`moderated_by`), Focal severity screening (`severity_screening_*`, below).
- **Expected empty?** No once any report has ever been submitted; normal to be empty on a completely fresh DB before `seed:diverse-reports` or a real submission.
- **Ownership:** Application, but `geom`/`pin_geom`/`exif_geom` are raw-PG-only — not in `schema.ts` (see the header comment there).
- **`elevation_m`:** no longer written since manuscript revision Phase 1, step 7a; existing values kept; columns dropped in Phase 8. New reports leave it NULL; nothing displays it any more.
- **`tracking_reference`** (Appendix H; manuscript revision Phase 2, step 2b, migration `0036_ticket_report_fields.sql`): `varchar(50) NOT NULL`, unique. Format `PRC-<YYYY>-<report id zero-padded to at least 6 digits>`, e.g. `PRC-2026-000123` (an id of 7+ digits is kept whole, never truncated), where YYYY is the submission year in Asia/Manila time (`created_at AT TIME ZONE 'Asia/Manila'` — a report sent at 00:30 on 1 January belongs to the new year). **Generated only by the `reports_fill_intake_fields` insert trigger** (below), never in TypeScript, so the app's submit, seeds and tests all get the same format; `ReportsService.submit` reads it back with `RETURNING` and returns it as `trackingReference`. Existing rows were backfilled by `0036` with the same expression. Shown to the citizen (submit message, My Reports, report detail) and to staff (Ticket Detail evidence list; Focal Intake's `reportReference`). Audit and notification text recorded before `0036` still says "Report #<id>" — history isn't rewritten.
- **`submitted_category`** (Appendix H; `0036`): `varchar(100) NOT NULL` — the category the citizen picked, never changed later (the ticket's `category` can be corrected from Phase 3; this column keeps what was submitted). `ReportsService.submit` writes it explicitly; the insert trigger fills it from the ticket's category when an insert leaves it NULL. `0036` backfilled existing rows from their ticket's *current* category — for the three categories renamed by `0035` that is the new manuscript name, not the exact string the citizen saw. Read (manuscript revision Phase 3, step 3e) only where it is shown as the citizen's own: Ticket Detail ("Citizen-reported category"), Focal Intake detail, and the citizen's report page ("You reported: …") when it differs from the ticket's current category. Every list, map, suggestion and export uses `tickets.category`.
- **The citizen's original location** (step 3e): `pin_geom` (and `geom`, `exif_geom`) are never changed after submission — a staff location correction moves only `tickets.geom` / `tickets.barangay_id`. Ticket Detail and Focal Intake detail show the pin ("Citizen pin: …") when it is 1 m or more from the ticket's current location.
- **Insert trigger `reports_fill_intake_fields`** (`0036`, BEFORE INSERT, per row): the single generator of `tracking_reference` and the fallback for `submitted_category`. It fills only a value left NULL (an explicit value is kept). `NEW.id` is already set when it runs — a serial id comes from its column default, which is applied before BEFORE ROW triggers — and `created_at` likewise (its `DEFAULT now()`; the trigger's `COALESCE(NEW.created_at, now())` only covers an explicit NULL).
- **`flags`** (`text[]`, nullable): the evidence-integrity flags (manuscript pp. 42–43, Appendix H REPORTS.flags; manuscript revision Phase 3, step 3b). Written once at submission by `ReportsService.submit` (`evidenceCheckFlags` in `api/src/reports/reports.service.ts`, which holds each number as a named constant); never block a submission; any non-empty array puts the report in the `/admin/flagged` queue. `submit()` stores `'{}'` for no flags; readers treat NULL and `'{}'` alike. Codes:
  | Code | Rule |
  |---|---|
  | `LOCATION_MISMATCH` | the photo has usable GPS and the pin is more than 50 m from it (`LOCATION_MISMATCH_THRESHOLD_M`; was 100 m). No usable GPS means no location flag at all. `location_mismatch_m` is stored whenever GPS exists, flagged or not |
  | `STALE_EVIDENCE` | the usable capture time is more than 24 h before submission (`STALE_EVIDENCE_HOURS`) **and** the submitted category (`submitted_category`) is time-sensitive: Localized Flooding, Rain-Induced Slope Failure/Landslide, Lahar or Volcanic Debris-Flow Threat (always, by group decision), Fallen Tree or Storm-Related Road Obstruction, or one of their legacy names (`STALE_EVIDENCE_CATEGORIES`). Other categories are never stale. Replaced `STALE_PHOTO` |
  | `MISSING_METADATA` | no usable capture time (`DateTimeOriginal` missing, unparseable, a zero date or before 2000). No staleness is inferred |
  | `TIMESTAMP_ANOMALY` | the capture time is more than 3 h after submission (`TIMESTAMP_ANOMALY_TOLERANCE_HOURS`); such a report is not checked for staleness. The 3 hours are a **study parameter chosen by the group** — the manuscript says only "implausible future capture time" |
  | `DUPLICATE_IMAGE:<report id>` | perceptual-hash (dHash) near-match against a report from the last 30 days — unchanged |
  | `BOUNDARY_FALLBACK:<barangay>:<m>` | the point missed every PSGC polygon but fell inside the OSM municipal envelope, so it was snapped to the nearest barangay — an **implementation extension** (not a manuscript flag), unchanged |

  The retired codes `STALE_PHOTO` (any category, measured against the server clock) and `NO_EXIF` (no GPS) no longer exist; the flag-type filter ignores them like any unknown value.
- **`exif_captured_at` / `exif_data`:** the capture time is EXIF `DateTimeOriginal` only (no fallback to other date fields), read as the camera's wall-clock time with the photo's own `OffsetTimeOriginal`, else `OffsetTime`, else Asia/Manila (UTC+08:00) — never the server's time zone (`parseCaptureTime`, `api/src/domain/media.service.ts`, step 3b). Before step 3b exifr turned it into a date in the **server's** time zone, so older stored times may be off by the server's offset. `exif_data` (stored only when the photo has GPS) also records `DateTimeOriginalOffset` and `DateTimeOriginalOffsetSource` for the offset used.
- **Migration `0040_evidence_flags.sql`** (step 3b; `pnpm --prefix api migrate:evidence-flags`, which prints `0040_evidence_flags.check.sql` before and after): recomputes only the managed codes on existing reports. It removes `LOCATION_MISMATCH`, `STALE_PHOTO`, `STALE_EVIDENCE`, `NO_EXIF` and `MISSING_METADATA`, keeps every other element in its order, then appends `LOCATION_MISMATCH` (stored `location_mismatch_m` > 50, distances not recomputed), `STALE_EVIDENCE` (old flags had `STALE_PHOTO`/`STALE_EVIDENCE` and `submitted_category` is time-sensitive) and `MISSING_METADATA` (`exif_captured_at` IS NULL). It **does not add `TIMESTAMP_ANOMALY` to old reports**, because their stored capture times may be shifted by the old server-time-zone bug, so a "future" time there proves nothing. Moderation columns are never touched; reports gaining a first flag join the pending queue, and reports left with no flags leave it (the check counts both). Only changed rows are updated, so a re-run updates 0.
- **Severity screening** (Appendix H REPORTS; manuscript Table 2; manuscript revision Phase 3, step 3f, migration `0041_severity_screening.sql`): Focal Personnel's advisory note on whether the citizen's severity needs operational validation.
  | Column | Type | Meaning |
  |---|---|---|
  | `severity_screening_status` | `severity_screening_status` enum (`NOT_REVIEWED` / `NO_CONCERN_NOTED` / `REQUIRES_OPERATIONAL_VALIDATION`), `NOT NULL DEFAULT 'NOT_REVIEWED'` | the current screening |
  | `severity_screening_remarks` | `text`, nullable | optional, trimmed, at most 1000 characters (checked by the app) |
  | `severity_screened_by_admin_id` | `integer`, nullable, **FK `admins(id)`** (Appendix H's FK, as in `routing_actions`) | the Focal screener |
  | `severity_screened_at` | `timestamptz`, nullable | when |

  - **CHECK `reports_severity_screening_consistency_check`:** `NOT_REVIEWED` has no screener and no time; any other status has both. Remarks are not part of the rule; `0041_severity_screening.check.sql` counts remarks on an unscreened report separately (expected 0).
  - **Writes:** only `FocalIntakeService.screenSeverity` (`POST /admin/intake/:reportId/severity-screening`, Focal Personnel only, while the ticket is active and not merged away). It sets all four fields (screener = the actor, time = `now()`); re-screening overwrites them; a screening is never set back to `NOT_REVIEWED`. Every screening writes a `report_severity_screened` audit event.
  - **Advisory only:** screening never changes `citizen_severity`, the ticket's severity (the median of its reports' `citizen_severity`, see `tickets` below) or Operational Priority.
  - **Reads:** Focal Intake (the intake state's "Screened", the intake detail's Severity screening card) and the operational Ticket Detail ("Focal screening: …" on each report). **Never in any citizen query or response.**
  - **Migration `0041`** (`pnpm --prefix api migrate:severity-screening`, which prints the check before and after): adds the enum, the four columns and the CHECK, all only if missing. **No backfill:** the old general screening action recorded no screening outcome, so every existing report starts `NOT_REVIEWED`, including reports with old `report_intake_actions` `'screened'` rows (the check counts those for information). Every run changes 0 rows.
- **Indexes:** `reports_geom_idx`/`reports_pin_geom_idx` (GIST, spatial). B-tree: `reports_ticket_id_idx` (join key into `tickets`, used by ticket detail/moderation/merge/dispute lookups), `reports_citizen_id_idx` ("My Reports" and per-citizen lookups), `reports_moderation_status_idx` (moderation queue's default `IS NULL`-pending view) — all added by `api/drizzle/0025_ticket_report_indexes.sql`, none modeled in `schema.ts` per this repo's raw-SQL-migration-owns-indexes convention. `reports_tracking_reference_unique` (UNIQUE, `0036`) enforces one reference per report; it is the one index mirrored in `schema.ts`, as `.unique()`, following the other unique columns there.

### `tickets`
- **Purpose:** The unit admins act on. New tickets carry exactly one report (no automatic merge since manuscript revision Phase 1, step 3); tickets created before that can represent several merged `reports`. Carries the full urgency/priority scoring output (`urgency_score`, `urgency_band`, `priority_score`, `urgency_level`, `priority_index` — see CLAUDE.md's Severity/Urgency/Priority terminology section for how these differ) plus lifecycle `status` and `assigned_office`.
- **Reads:** Ticket Queue, Map, Dashboard, urgency recompute (`RecomputeService`).
- **Writes:** Ticket creation for every new report, status transitions (`StatusHistory` insert alongside), urgency recompute (on-demand, per CLAUDE.md's Urgency triage section), office reassignment.
- **Expected empty?** No once any report has ever been submitted.
- **Ticket severity is not stored** (manuscript pp. 73–74; manuscript revision Phase 4, step 4a). There is no severity column on `tickets`: it is derived from the member reports' `reports.citizen_severity` whenever it is needed, only by `ticketSeverity` in `api/src/common/utils/severity.ts`. Member reports are every report linked to the ticket (`reports.ticket_id`); moderation does not remove one, and a removed/regrouped report or a merged-away ticket's reports have moved. The **Severity Factor** is the median of the members' factors (Low 0.25 / Medium 0.50 / High 0.75 / Critical 1.00), for an even count the mean of the two middle factors, and for one report its own factor — so it can fall between levels (0.375 / 0.625 / 0.875). Operational Priority (`priority_index`) uses that number exactly. The **label** shown on Ticket Detail is derived from it: the nearest level, and exactly halfway rounds **up** (0.625 → High). Each report keeps its own `citizen_severity`. It replaced the old `MAX` rule; `priority_index` is the only stored value it affects, recalculated inside merge / remove / regroup / location-correction transactions for the changed tickets and for every active ticket on the usual triggers. `pnpm --prefix api recalc:median-severity` (dry run unless `--apply`) recalculates every active, not merged-away ticket at once, writing only `priority_index` where it changes — no `updated_at`, no audit event; Resolved/Rejected keep their last value.
- **Ownership:** Application, but `geom` is raw-PG-only (not in `schema.ts`).
- **Indexes:** `tickets_geom_idx` (GIST, spatial). B-tree: `tickets_office_status_idx` (composite, `assigned_office`+`status` — the combined filter shape used by the admin Ticket Queue and most Dashboard queries), `tickets_status_idx` (status-only filtering for queries with no office scope — public hazard map, urgency recompute), `tickets_barangay_id_idx` (barangay-scoped filters/joins) — all added by `api/drizzle/0025_ticket_report_indexes.sql`, none modeled in `schema.ts`. `tickets_merged_into_ticket_id_idx` (`0036`, for the Phase 3 merge lookups), likewise not modeled. The suggested-related-ticket search (`RelatedTicketsService`, manuscript revision Phase 3, step 3c) is read-only and uses `tickets_geom_idx` through a bounding-box test (`t.geom && ST_Envelope(ST_Buffer(v.geom::geography, radius + 1)::geometry)`) before `ST_DWithin` on geography decides in metres; no new index.
- **`category`:** Free-form `text`, not a database enum — validated only at the application layer. New submissions validate against `CATEGORIES` in `api/src/contracts/schemas.ts` (13 values: replaced in full by a Phase 3 follow-up — manuscript alignment — then renamed and split in manuscript revision Phase 2, step 2a, below); admin-side filter/query validation additionally accepts `LEGACY_CATEGORIES` (the 11 pre-follow-up values plus the 4 retired in Phase 2, step 2a) via the combined `ALL_CATEGORIES`, since historical tickets, reports' audit/notification text and old bookmarks still carry them and must stay filterable. Drives automatic office routing at ticket creation (`officeForCategory`/`categoryRouting`, `api/src/common/utils/office.ts`) and the dedup-merge radius (`radiusForCategory`, `api/src/common/utils/radius.ts`); never re-derived after creation. Not nullable. **No historical row's `category` value was changed by the Phase 3 follow-up** — this is an additive validation-list swap, not a backfill; every legacy value keeps working exactly as before in routing, marker/icon display, dashboard distribution, and CSV export.

  **Manuscript revision Phase 2, step 2a (handoff Decisions 6, 9, 13)** does change stored values, through migration `0035_categories_manuscript.sql` (script `migrate:categories-manuscript`, which prints before/after counts from `0035_categories_manuscript.check.sql` and also rewrites the same three names in `admin_saved_views.query`, both surfaces, in one transaction). History tables — `admin_audit_events`, `notifications`, `status_history` — are not rewritten and keep whatever category text they recorded.

  | Retired value (still a valid legacy value) | New submissions use | On existing tickets (0035) | Office |
  |---|---|---|---|
  | `Drainage / Culvert / Manhole Issue` | `Damaged Manhole Cover` (20 m grouping radius) or `Clogged Drainage / Damaged Culvert` (50 m) — split, Decision 6 | **kept**; `category_review_required` set to `true` (Decision 13) — the right half can't be derived from the data, so staff correct it (Phase 3) | MEO, direct |
  | `Landslide / Slope Failure` | `Rain-Induced Slope Failure/Landslide` (Decision 9) | renamed | MDRRMO, direct |
  | `Lahar / Debris-Flow Threat` | `Lahar or Volcanic Debris-Flow Threat` (Decision 9) | renamed | MDRRMO, direct |
  | `Fallen Tree / Storm-Related Obstruction` | `Fallen Tree or Storm-Related Road Obstruction` (Decision 9) | renamed | MDRRMO, direct |

  Routing and grouping radius are unchanged for every existing value; the old keys stay in `office.ts`, `radius.ts` and `lib/gis/categoryMarker.tsx` so legacy tickets keep their routing and marker.

  New categories with no pre-follow-up predecessor: `Rain-Induced Slope Failure/Landslide`, `Lahar or Volcanic Debris-Flow Threat` (both MDRRMO, direct), and `Damaged Manhole Cover` (MEO, direct; split off the combined drainage category in Phase 2, step 2a).
- **`assigned_office`:** A genuine Postgres enum (`office`, `MEO`/`MDRRMO` only — `officeEnum` in `schema.ts`), unlike `category`. Set once at creation from `categoryRouting(category).office`; changed afterward only by a manual Reassign (`POST /admin/tickets/:id/reassign`, Focal's `POST /admin/intake/:reportId/reassign`, or a staff category correction to the other office), each recorded in `office_reassignments` and `routing_actions` with its reason — a merge never changes it (manuscript revision Phase 5, step 5a). Every category also carries a `directResponsibility` flag (computed live from `category`, never stored) distinguishing an office's own direct repair responsibility from a Referral/coordination concern it merely holds custody of — see [`features.md`](features.md) §1.
- **Hazard Urgency columns (`elevation_m`, `elevation_factor`, `precipitation_factor`, `cluster_factor`, `urgency_score`, `urgency_band`, `priority_score`, `urgency_level`):** no longer written since manuscript revision Phase 1, step 7a; existing values kept; columns dropped in Phase 8. New tickets leave all eight NULL (`ReportsService.submit` no longer looks up elevation or rain, and `RecomputeService` was deleted). The notes below describe how they were written before step 7a.
- **`elevation_factor`/`precipitation_factor`/`cluster_factor`:** The three stored per-factor inputs behind `urgency_score`, each 0–1, rewritten by `RecomputeService.recomputeActiveTicketUrgency` on every recompute (only for tickets in `Reported`/`Under Review`/`In Progress` — resolved/rejected tickets keep whatever they last held). Surfaced as the Ticket Detail urgency decomposition. See [`triage-model.md`](triage-model.md) for what each factor means and the exact formula/weights. `urgency_band` and `urgency_level` are both derived from the same threshold function as of Phase 2 of the manuscript-alignment work — they cannot disagree.
- **`resolution_image_url`/`resolution_notes`:** Set when an admin advances a ticket to `Resolved` through the resolve dialog (`TicketsService`, `POST /admin/tickets/:id/status`). Both are **citizen-visible** — they render in the Case Closure Summary on the citizen's report detail page, so they are staff-authored for a public audience, unlike `work_orders.notes` (internal-only). Nullable: a ticket can be resolved with neither.
- **`disputed_at`/`dispute_reason`:** The ticket-level dispute flag. Since manuscript revision Phase 3, step 3g each citizen's own answer lives in `resolution_feedback` (below); these two columns are a **mirror kept until Phase 8**, written by `ReportsService.answerResolution` (`POST /reports/mine/:id/dispute`): the **first** dispute on a ticket sets both (`WHERE disputed_at IS NULL`), later disputes by other citizens leave them as they are (but each still notifies the office). NULL means no citizen has disputed. It never rolls `status` back and is never a scoring input (never touches `priority_index`). Cleared by nothing. Still the only source for the admin Ticket Queue's "Disputed only" filter, Disputed tab count and row badge, and Ticket Detail's header badge and red "Citizen reports issue not fixed" card (date + `dispute_reason`). Citizens no longer receive it: their report detail carries only their own answer (`my_feedback`).
- **`resolution_confirmed_at`:** The ticket-level confirmation mirror, kept until Phase 8 like `disputed_at`: the first confirmation sets it, and only while the ticket has no dispute and no earlier confirmation — exactly the old `UPDATE ... WHERE resolution_confirmed_at IS NULL AND disputed_at IS NULL`. A confirmation after another citizen's dispute is stored in `resolution_feedback` but leaves this NULL. No screen reads it any more (the citizen page reads `my_feedback`; staff read the `resolution_feedback` counts). Never a scoring input, never touches `status`.
- **`category_review_required`:** `boolean NOT NULL DEFAULT false`. **Implementation extension (handoff Decision 13) — not in the manuscript's data dictionary; flag it for the next ERD/data dictionary update.** Added and set by migration `0035_categories_manuscript.sql` on tickets still carrying the retired combined `Drainage / Culvert / Manhole Issue` category, which can't be split automatically into `Damaged Manhole Cover` / `Clogged Drainage / Damaged Culvert`. Cleared by the staff category correction (`TicketCorrectionsService.correctCategory`, manuscript revision Phase 3, step 3e); nothing else writes it. Read by the Ticket Queue (`categoryReview=true` filter, also honored by the tickets CSV export through `parseTicketQuery`, and a "Category review" row badge) and Ticket Detail ("Category review needed" header badge). Never a scoring input, never touches `status` or `priority_index`.
- **`initial_assigned_office`** (Appendix H; manuscript revision Phase 2, step 2b, migration `0036_ticket_report_fields.sql`): `office NOT NULL` (the same enum as `assigned_office`) — the office automatic Initial Routing first assigned, preserved after any reassignment. `ReportsService.submit` writes it explicitly (= the routed office); the `tickets_fill_initial_assigned_office` BEFORE INSERT trigger fills it from `assigned_office` for any insert that leaves it NULL (seeds, tests), so it is never missing. `0036` backfilled it from the `from_office` of the ticket's **earliest** `office_reassignments` row (by `reassigned_at`, then `id`), else `assigned_office`. Shown only on Ticket Detail, as "Initially routed to {office}" when it differs from `assigned_office`.
- **`resolution_outcome`** (Appendix H; `0036`): nullable enum `resolution_outcome` (`MUNICIPAL_ACTION_COMPLETED` | `EXTERNAL_REFERRAL` — `resolutionOutcomeEnum` in `schema.ts`). `TicketsService.advanceStatus` sets `MUNICIPAL_ACTION_COMPLETED` in the same UPDATE that resolves a ticket (bulk advance never resolves — it skips tickets whose next status is Resolved); rejecting leaves it NULL, as do active tickets. `EXTERNAL_REFERRAL` can't be chosen anywhere yet (Phase 5). `0036` backfilled `MUNICIPAL_ACTION_COMPLETED` on every `Resolved` ticket. Shown only on Ticket Detail ("Outcome: Municipal action completed" beside the status pill, Resolved tickets). Never a scoring input.
- **`merged_into_ticket_id`** (`0036`): nullable `integer`, FK → `tickets(id)` (`tickets_merged_into_ticket_id_tickets_id_fk`). **Implementation extension (handoff Decision 11) — not in the manuscript's data dictionary; flag it for the next ERD/data dictionary update.** Set by the staff Merge (`TicketGroupingService.merge`, manuscript revision Phase 3, step 3d) on the ticket merged away, pointing at the survivor; never cleared. A merged-away ticket keeps its status, `member_count`, `status_history` and Work Orders unchanged as history; its reports move to the survivor. Read by: the Ticket Detail banner and "Includes reports merged from" line (`TicketsService.getTicketDetail`, with the `ticket_merged` audit event for who/when/why), and every list, count and recalculation that must leave merged-away tickets out (`merged_into_ticket_id IS NULL`: the Ticket Queue and its counts, the admin map, the dashboard, Barangay Insights, the public map, related candidates, the Operational Priority recompute; the tickets CSV keeps them only for `status=all`, with a "Merged into" column). Every ticket write refuses a merged-away ticket (409). The survivor's `member_count` and `flagged` are refreshed from its reports in the same transaction (`flagged` only ever turns on).
- **Insert trigger `tickets_fill_initial_assigned_office`** (`0036`, BEFORE INSERT, per row): the single generator of the `initial_assigned_office` default (see above); like the reports trigger, it fills only a NULL value.

### `routing_actions`
- **Purpose:** The manuscript's ROUTING_ACTIONS table (Appendix H; manuscript revision Phase 2, step 2c, migration `0037_routing_actions.sql`): one row per office reassignment (`action_type` `REASSIGN`) or external referral (`REFER`). Columns: `ticket_id` (FK → `tickets`), `action_type` (enum `routing_action_type`), `from_office`/`to_office` (the `office` enum, nullable), `referral_target` (`varchar(255)`, the agency), `reason` (`text NOT NULL`), `admin_id`, `admin_name` (`varchar(100)`), `created_at`. Indexed on `(ticket_id, created_at)`.
- **Reads:** The routing rule's no-op check (`TicketsService.logReferral` reads the ticket's latest row, see below) and Ticket Detail's timeline, which joins a REASSIGN row's reason onto its `office_reassignments` row (same ticket, `to_office` and timestamp). The timeline and referral list otherwise still read `office_reassignments` and the `ticket_referral_noted` audit events (whose metadata carries the same agency and reason) — moving those reads here is not part of step 5a.
- **Writes:** `TicketsService.reassignOffice` (every caller: the Ticket Detail Reassign dialog, bulk reassign, Focal's Reassign on Focal Intake — `POST /admin/intake/:reportId/reassign`, which replaced Forward in manuscript revision Phase 5, step 5a — and the demo seed) writes a `REASSIGN` row in the same transaction as its `office_reassignments` row; `TicketsService.logReferral` (the Refer dialog on Ticket Detail and Focal Intake) writes a `REFER` row in the same transaction as its `ticket_referral_noted` audit event — `referral_target` = the trimmed agency exactly as stored in the event's metadata, `from_office` = the ticket's current office, `to_office` NULL. Both insert `created_at = now()`, which in the same transaction equals the source row's own timestamp. `admin_name` is the session name cut to 100 characters (admin names have no length limit; `ROUTING_ADMIN_NAME_MAX_LENGTH`).
- **Reason (Phase 5, step 5a):** required for both actions — trimmed, 1–1000 characters (`validateRoutingReason`, `api/src/admin/ticket-routing.rules.ts`), stored as given. Every write is checked first, on the ticket row locked `FOR UPDATE` in the same transaction, by the one routing rule: Focal Personnel only while the ticket is `Reported` with no pending/in-progress Work Order; MEO/MDRRMO Personnel on their own office's tickets; nobody on a merged-away or `Rejected` ticket or while a Work Order is pending/in progress; the System Administrator never. A Reassign to the current office and a Refer to the agency the ticket's latest `routing_actions` row already referred it to (case-insensitive; a Reassign since then makes it a real referral again) are refused as no-ops, and MEO/MDRRMO are never a `referral_target`. A staff category correction (manuscript revision Phase 3, step 3e) that moves the ticket runs the same Reassign code path (`TicketsService.assertCanReassign` + `writeReassignment`) with the correction's reason.
- **Placeholder reason (history only):** `Reason not recorded (before reasons were required)` (`ROUTING_REASON_NOT_RECORDED` in `schema.ts`) — the `0037` backfill's reason for older reassignments and note-less referrals, and what the app wrote before step 5a. Nothing writes it any more; those rows are never rewritten. Ticket Detail's timeline shows a REASSIGN row's reason when it isn't the placeholder.
- **Backfill (`0037`):** REASSIGN — one row per `office_reassignments` row: the same from/to office, `admin_id`, `admin_name` = the snapshot name, else the admin's current `first_name || ' ' || last_name`, `created_at = reassigned_at`, no `referral_target`. REFER — one row per `ticket_referral_noted` audit event on a ticket: `referral_target = metadata.agency`, `to_office` NULL, `from_office` = the `to_office` of the ticket's latest reassignment at or before the event, else `tickets.initial_assigned_office` (so `0037` runs after `0036`), the actor as admin, `created_at` = the event's, `reason` = the note when it isn't blank. Each insert skips a row already present with the same `ticket_id`, `action_type`, `created_at` and (null-safe) `from_office`/`to_office`/`referral_target` — the app's own rows share that key, so re-running inserts 0 rows. A guard stops the whole migration, before anything is created, if a source row has no admin, names an admin that no longer exists, has a name over 100 characters, points at a missing ticket, or has an agency over 255 characters; nothing is invented or skipped. `0037_routing_actions.check.sql` reports the guard counts before the run and, after it, source rows with no routing row, duplicate key groups and NULL `from_office` (all must be 0). Run with `pnpm --prefix api migrate:routing-actions`.
- **FK note:** `admin_id` has a real FK to `admins(id)`, as Appendix H defines it — an intentional departure from the FK-less actor-snapshot convention of `office_reassignments`, `status_history` and `admin_audit_events`. An admin referenced here can no longer be deleted. The app never deletes admins (it deactivates them); the one script that does, `cleanup-e2e-admins.ts` (Playwright global setup, `e2e-%` accounts only), still works because no throwaway e2e admin reassigns or refers — its own comment, which says no table references `admins(id)`, is out of date for this table.
- **Expected empty?** Normal to have few or zero rows, like `office_reassignments`.
- **Ownership:** Application (Drizzle models it; the index is raw SQL only).

### `resolution_feedback`
- **Purpose:** The manuscript's RESOLUTION_FEEDBACK table (Appendix H; manuscript revision Phase 3, step 3g, migration `0042_resolution_feedback.sql`): each reporter's own answer on a `Resolved` ticket — `CONFIRMED` (it was fixed) or `DISPUTED` (it was not, with a reason). Columns: `id`, `ticket_id` (FK → `tickets`), `citizen_id` (FK → `citizens`), `feedback_type` (enum `resolution_feedback_type`: `CONFIRMED` | `DISPUTED`), `reason` (`text`, nullable), `created_at`.
- **Answers are one-time and locked:** `UNIQUE (ticket_id, citizen_id)` (`resolution_feedback_ticket_citizen_unique`) — a citizen answers a ticket once, a second answer is a 409 that changes nothing, and one citizen's answer never blocks another's. CHECKs: `resolution_feedback_disputed_reason_check` (a `DISPUTED` row needs a non-empty reason) and `resolution_feedback_confirmed_reason_check` (a `CONFIRMED` row has `reason` NULL). Indexes `resolution_feedback_ticket_id_idx`, `resolution_feedback_citizen_id_idx`.
- **Writes:** `ReportsService.answerResolution`, behind the unchanged routes `POST /reports/mine/:id/confirm-resolution` and `POST /reports/mine/:id/dispute`: the report must be the citizen's (404 otherwise), its ticket is followed through `merged_into_ticket_id` to the survivor (rows are never written against a merged-away id), the citizen must have a report on the survivor or on a ticket merged into it (403), and the survivor must be `Resolved` (400). The insert (`ON CONFLICT (ticket_id, citizen_id) DO NOTHING`, under the ticket's row lock) and the ticket-level mirror (`tickets.disputed_at`/`dispute_reason`/`resolution_confirmed_at`, see above) and, for a dispute, the office `ticket_disputed` notification are one transaction. No audit event (the audit log is for staff actions); the notification carries no citizen id.
- **Reads:** the citizen's report detail (`getMyReportDetail`, `my_feedback`: their own row only, joined on the report's own citizen — never another citizen's answer or any count); staff Ticket Detail (`TicketsService.getTicketDetail`, `citizenFeedback`: confirmed/disputed counts and every answer's type, reason and time, with no citizen name, id or contact — Ticket Detail shows no reporter identity).

One row per ticket with old feedback: `DISPUTED` with `dispute_reason` and `created_at = disputed_at`, else `CONFIRMED` with `created_at = resolution_confirmed_at`. ### `hazard_information`
- **Purpose:** The manuscript's HAZARD_INFORMATION table (pp. 71–72, Appendix H; manuscript revision Phase 4, step 4b, migration `0043_hazard_information.sql`): the DENR-MGB susceptibility at a ticket's representative location (`tickets.geom`). **Advisory only** — the source's own code and wording, never turned into a PORAC-SDSS risk, urgency, severity or score, and it never feeds `priority_index`, report validity, Work Orders or assessments. Columns: `id`, `ticket_id` (FK → `tickets`, NOT NULL), `hazard_context_type` (enum `hazard_context_type`: `FLOOD` | `RAIN_INDUCED_LANDSLIDE`), `lookup_status` (enum `hazard_lookup_status`: `CLASSIFIED` | `NO_CLASSIFICATION` | `TEMPORARILY_UNAVAILABLE`), `susceptibility_code` (`varchar(20)`), `susceptibility_label` (`varchar(100)`), `query_geom` (`geometry(Point, 4326)`, NOT NULL — the point actually looked up), `failure_reason` (`text`), `looked_up_at` (`timestamptz`, default `now()`), `superseded_at` (`timestamptz`).
- **Which categories:** Localized Flooding (and legacy `Flooding`) → DENR-MGB Detailed Flood Susceptibility, field `FloodSusc` (`VHF`/`HF`/`MF`/`LF`). Rain-Induced Slope Failure/Landslide (and legacy `Landslide / Slope Failure`) → Detailed Rain-induced Landslide Susceptibility, field `LndslideSusc` (`VHL`/`HL`/`ML`/`LL`/`DF` — debris-flow path; that layer's polygons are very large, which is the source's data). Lahar or Volcanic Debris-Flow Threat: **no automated classification in this version**. Every other category: **not applicable**. Neither of the last two ever gets a row. The code → label map (`HAZARD_LAYERS` in `api/src/common/utils/hazard-information.ts`) is the layers' own legend wording, verified from each layer's `?f=json` metadata (the layers carry no coded-value domain); an unrecognised code is stored with `susceptibility_label` NULL rather than invented wording.
- **Lookup status:** `CLASSIFIED` = the point is inside a source polygon (its code). `NO_CLASSIFICATION` = no polygon at the point; shown as "No DENR-MGB classification at this location", **never** as Low or safe. `TEMPORARILY_UNAVAILABLE` = timeout (8 s, single attempt), network error, non-200, unparsable JSON, or an ArcGIS `error` object (which the source sends with HTTP 200), with `failure_reason` saying which.
- **Constraints:** CHECKs `hazard_information_classified_check` (`CLASSIFIED` has a code), `hazard_information_no_classification_check` (`NO_CLASSIFICATION` has no code and no label), `hazard_information_unavailable_check` (`TEMPORARILY_UNAVAILABLE` has a non-blank `failure_reason` and no code or label). Partial unique index `hazard_information_current_unique` on `(ticket_id, hazard_context_type) WHERE superseded_at IS NULL` — at most one current row per ticket and context type. Indexes `hazard_information_ticket_id_idx` and the GiST `hazard_information_query_geom_idx`.
- **Superseded rows are history:** each lookup supersedes the ticket's current row(s) (`superseded_at = now()`) and inserts the new one in one transaction; nothing is updated in place or deleted. A ticket whose category changes to Lahar or another category gets its current row superseded and no new row. Ticket Detail treats a current row as current only while it matches the ticket's present category (context type) and location (`ST_Equals(query_geom, tickets.geom)`); otherwise it is shown as history and the ticket as "Not yet checked" until the new lookup lands.
- **Writes:** `HazardInformationService.lookup` (`api/src/domain/hazard-information.service.ts`), always after the originating transaction has committed, fired and **not awaited** (a slow or failed source never blocks or delays the request), one lookup per ticket at a time: on a new ticket in an applicable category (`ReportsService.submit`), on a location correction and on a category correction (`TicketCorrectionsService`). Not on merge, remove or regroup. Merged-away tickets are skipped. `HAZARD_INFORMATION_LOOKUPS=disabled` (API env) turns every lookup into a no-op that writes nothing — used for Playwright runs, which must never call the live service.
- **Retry rule (implementation extension, not in the manuscript):** (a) `POST /admin/tickets/:id/hazard-information/retry` — operational staff of the ticket's office (same 403/404 as Ticket Detail), 409 for a merged-away or closed ticket or a category without a lookup, **429** within 60 s of the ticket's last attempt ("…checked less than a minute ago. Try again in N s."); waits for the lookup and returns the new state. (b) Opening Ticket Detail starts a background lookup (not awaited) when an active, not merged-away ticket in an applicable category has no current row ("Not yet checked") or its current row is `TEMPORARILY_UNAVAILABLE` and over 10 minutes old. Closed (Resolved/Rejected) tickets never auto-retry; they keep what they have. The earlier group note of a cron retry (max 20 tickets per run) was not built; this rule replaces it.
- **Reads:** staff Ticket Detail (`GET /admin/tickets/:id` → `hazardInformation`: applicability, current row, up to 10 earlier rows); the Ticket Queue and the dashboard's Highest Priority Actions (`GET /admin/tickets` rows' `hazard_summary`, e.g. "Flood: MF (Moderate Susceptibility to Flooding)"); the tickets CSV export ("Hazard Information" column). **Citizens never get Hazard Information** from any endpoint.
- **Backfill:** none in the migration (the table starts empty). `pnpm --prefix api backfill:hazard-information` (`api/scripts/backfill-hazard-information.ts`) is a dry run by default — no network call, no write — counting active, not merged-away tickets in an applicable category with no current row, by category. `--apply` looks them up one at a time, oldest first, about 500 ms apart, through the same service (failures stored as `TEMPORARILY_UNAVAILABLE` for the auto-retry); `--limit N` caps a run; tickets that already have a current row are skipped, so it is safe to re-run.
- **Coverage caveat:** the source's Porac coverage (both layers answer; empty results are common; 2–8 s responses) was tested from a laptop browser only. It still needs a check from the deployed backend (Railway) before it is relied on.
- **Expected empty?** Yes until the backfill or the first lookups run; afterwards one current row per active flood/landslide ticket plus history.
- **Ownership:** Application, raw PG only (geometry column): the table is not modelled in Drizzle (listed in `schema.ts`'s non-Drizzle comment block); only its two enums are (`hazardContextTypeEnum`, `hazardLookupStatusEnum`).

### `rainfall_context`
- **Purpose:** The manuscript's RAINFALL_CONTEXT table (p. 72, Appendix H; manuscript revision Phase 4, step 4c, migration `0044_rainfall_context.sql`): the current rainfall at a ticket's representative location (`tickets.geom`), for active **Localized Flooding** and **Rain-Induced Slope Failure/Landslide** tickets (legacy `Flooding` / `Landslide / Slope Failure` the same). Every other category, Lahar included, is **not applicable** and never gets a row. Kept **separately from `hazard_information`**. **Advisory and staff-only**: never a score, and it never changes `priority_index`, DENR-MGB Hazard Information, report validity or any rule. Columns: `id`, `ticket_id` (FK → `tickets`, NOT NULL), `status` (enum `rainfall_context_status`: `CURRENT` | `STALE` | `UNAVAILABLE`), `rainfall_mm` (`real`, NULL only for `UNAVAILABLE`), `source_provider` (`varchar(100)` NOT NULL), `observation_at` (`timestamptz`), `fetched_at` (`timestamptz` NOT NULL, default `now()`), `query_geom` (`geometry(Point, 4326)` NOT NULL — the ticket location the reading is for), `failure_reason` (`text`), `superseded_at` (`timestamptz`).
- **Provider and value:** OpenWeatherMap Current Weather (`/data/2.5/weather`, `source_provider = 'OpenWeatherMap'`, key `OPENWEATHERMAP_API_KEY`). `rainfall_mm` is the response's `rain["1h"]`, the rain over **the last hour** in mm, shown as "Rainfall (last hour)". `observation_at` is the provider's own `dt` (when it calculated the data), not the fetch time. The provider leaves `rain` out when it isn't raining, so **only an HTTP 200 with a numeric `dt` and no `rain` object is a real 0 mm**; no `dt`, a `rain` object without a usable `1h` value, a non-200, a timeout (5 s, single attempt), a network error or unparsable JSON is a failure. A failure is **never stored or shown as 0 mm**. The API key is never logged or stored: `failure_reason` and log lines pass through `redactSecrets` (`appid=…` and the key itself replaced); a provider error message (e.g. an invalid key) is kept, redacted.
- **Status meaning:** `CURRENT` = a good reading (0 is valid). `STALE` = a refresh failed after an earlier good reading — **the A1 rule**: that row is **updated in place** to `STALE`, keeping its `rainfall_mm`, `observation_at` and `fetched_at`, with `failure_reason` saying why the refresh failed; shown as "Last known: N mm … Could not refresh". `UNAVAILABLE` = a fetch failed with no earlier value for this location: no `rainfall_mm`, `fetched_at` = the attempt. A value older than the 10-minute reuse window with no failed refresh is simply refreshed the next time Ticket Detail is opened. The in-place `STALE` update is the one exception to "supersede, never update": it records that the last good value could not be refreshed, and changes nothing else. A failure after a **category** correction at the same location supersedes the current row and inserts a new `STALE` row carrying the same value and times (so the change stays as history); a failure after a **location** correction inserts `UNAVAILABLE`, because the earlier value was for another place.
- **Constraints:** CHECKs `rainfall_context_current_check` (`CURRENT` has `rainfall_mm >= 0` and no `failure_reason`), `rainfall_context_stale_check` (`STALE` has `rainfall_mm >= 0` and a non-blank `failure_reason`), `rainfall_context_unavailable_check` (`UNAVAILABLE` has no `rainfall_mm` and a non-blank `failure_reason`); NaN and Infinity are rejected (`< 'Infinity'::real`). Partial unique index `rainfall_context_current_unique` on `(ticket_id) WHERE superseded_at IS NULL` — at most one current row per ticket. Indexes `rainfall_context_ticket_id_idx` and the GiST `rainfall_context_query_geom_idx`.
- **Reuse:** (a) the ticket's own current row is reused as is while its `fetched_at` is within 10 minutes (Ticket Detail only). (b) **Same-location cache across tickets**: an in-memory map in the API process keyed by the point **rounded to 4 decimals** (about 11 m at Porac's latitude; `rainfallLocationKey`), successful readings only, 10-minute TTL from the provider fetch; the provider is asked at exactly that rounded point. Tickets this close share one reading; OpenWeatherMap's own grid is far coarser, so a finer key would only repeat calls, and a coarser one would stretch "same location". A cached reading is written with its original `fetched_at`. The cache is per process and empties on restart.
- **Writes:** `RainfallContextService.refresh` (`api/src/domain/rainfall-context.service.ts`), always **after** the originating transaction has committed, fired and **not awaited**, one refresh per ticket at a time, under the ticket row lock, rechecking status, category and location before writing: (a) opening Ticket Detail, when an active, not merged-away applicable ticket has no current row for its location or one fetched more than 10 minutes ago (a 60 s per-ticket cooldown after a failed call stops an outage being hammered); (b) a location or category correction (`TicketCorrectionsService`): the current row is superseded and kept as history, then re-fetched (the same-location cache may answer); a category without rainfall context only supersedes. (c) **Refresh** — `POST /admin/tickets/:id/rainfall-context/refresh`, operational staff of the ticket's office (same 403/404 as Ticket Detail), **409** for a merged-away or closed ticket or a non-applicable category, **429** within 60 s of the ticket's last check ("Rainfall for Ticket #N was checked less than a minute ago. Try again in N s."); always asks the provider (neither reuse applies) and waits for the result; **500** "Rainfall could not be recorded for Ticket #N. Try again later." when the row could not be written (the automatic Ticket Detail and correction refreshes stay silent and log a warning). Not on report submission, merge, remove or regroup. Closed (Resolved/Rejected) and merged-away tickets are never refreshed and keep their rows. Nothing is ever deleted. Timestamps reach the SQL as ISO strings with `::timestamptz` casts, never `Date` objects: `DbModule`'s `drizzle(pg)` replaces the shared client's timestamp serializers with pass-throughs, so a `Date` parameter throws (the bug that kept every row from being written on production right after 4c).
- **Kill switch:** `RAINFALL_LOOKUPS=disabled` (API env; default `enabled` when unset) makes every refresh a no-op that writes nothing; stored rows are still shown. Used for Playwright runs, which must never call the live service. Don't set it anywhere permanent.
- **Reads:** staff Ticket Detail only (`GET /admin/tickets/:id` → `rainfallContext`: `applicability` `applicable` | `not_applicable` | `closed_historical` (Resolved, Rejected or merged away), `valueLabel`, the current row for the ticket's present location, up to 10 earlier rows newest first). A current row at an old location is shown as history and the ticket as "Not yet fetched" until the new reading lands. Not in the Ticket Queue, dashboard or any CSV export. **Citizens never get rainfall context** from any endpoint.
- **Backfill:** none; the table starts empty and fills as Ticket Detail is opened.
- **Reachability caveat:** OpenWeatherMap was not called from the deployed backend (Railway) in this step, and the key in each environment was not checked. Confirm both there before relying on it (a `CURRENT` reading after opening an active flood ticket, not `UNAVAILABLE` with "HTTP 401").
- **Expected empty?** Yes until applicable tickets are opened; afterwards one current row per opened active flood/landslide ticket plus history.
- **Ownership:** Application, raw PG only (geometry column): the table is not modelled in Drizzle (listed in `schema.ts`'s non-Drizzle comment block); only its enum is (`rainfallContextStatusEnum`).

### `report_intake_actions`
- **Purpose:** Append-only Focal intake activity trail — forwarded/escalated (five-role Batch 2); **history only since manuscript revision Phase 5, step 5a**, which removed Forward and Escalate (manual routing is only Reassign or Refer, recorded in `routing_actions`). Never a mutable "intake status" column: the admin-facing New/Acknowledged/Screened/Forwarded/Escalated display state is always *derived* at query time from this table, `report_acknowledgments` and the report's severity screening (`FocalIntakeService.deriveIntakeState`), never persisted as its own state machine — this is what keeps intake state from ever becoming a second `TicketStatus`.
- **Reads:** `FocalIntakeService.listIntake`/`getIntakeDetail`/`listIntakeGeo` — the latest `forwarded`/`escalated` row for the intake state, and every row for the intake detail's activity list.
- **Writes:** None since Phase 5, step 5a. `FocalIntakeService.forward`/`escalate` (and their `POST /admin/intake/:reportId/forward|escalate` routes) wrote the `forwarded`/`escalated` rows until then; the rows are kept, still shown in the intake detail's activity list and still read for the derived Forwarded/Escalated intake state, never rewritten. Old `report_escalated` audit events stay too.
- **Old `'screened'` rows (history):** the old general screening action (Initial Screening, a continue/forward/escalate recommendation) wrote `'screened'` rows. Group decision, manuscript revision Phase 3, step 3f: severity screening (`reports.severity_screening_*`) **replaces** it. The old rows are kept, shown in the intake detail's activity list as "Initial screening completed", never written again, and **not** read for the intake state: "Screened" now means the report's `severity_screening_status` is not `NOT_REVIEWED`, and those reports start `NOT_REVIEWED`. When a report has both a forward/escalation and a severity screening, the later of the two decides the state.
- **Expected empty?** Normal to be sparsely populated.
- **Ownership:** Application (Drizzle).
- **Note:** `action_type` is plain text (validated against a TS union in the service layer, not a pg enum), matching `notifications.type`/`admin_audit_events.action_type`'s existing convention for a still-evolving vocabulary.

### `operational_assessments`
- **Purpose:** MEO/MDRRMO's human Operational Assessment (five-role Batch 3) — the third decision-support layer, alongside the two system-generated ones (Hazard Urgency = `tickets.priority_score`/`urgency_level`, Operational Priority = `tickets.priority_index`). **One current row per ticket — `ticket_id` is `UNIQUE`.** Deliberately not a revision-history table; a later save updates the existing row in place via `INSERT ... ON CONFLICT (ticket_id) DO UPDATE`, never a second row.
- **Reads:** Folded into `GET /admin/tickets/:id`'s response (`operationalAssessment: null | {...}`) — no second frontend fetch.
- **Writes:** `OperationalAssessmentService.upsert` only, via `POST /admin/tickets/:id/assessment`.
- **Expected empty?** Normal to be empty until the first assessment is saved — not part of every ticket's lifecycle.
- **Ownership:** Application (Drizzle).
- **Note:** Two actor snapshots, not one — `assessed_by_admin_id`/`assessed_by_name`/`assessed_at` capture who *first created* the row and never change on edit; `updated_by_admin_id`/`updated_by_name`/`updated_at` capture whoever most recently edited it. This is what makes the office-transfer case legible (ticket reassigned MEO → MDRRMO: MDRRMO can edit the existing row, and `updated_by_*` shows that happened without losing who created it). The `ON CONFLICT DO UPDATE SET` clause deliberately omits `assessed_by_*`/`assessed_at`, so a conflicting write (either a genuine edit or two admins racing the first save) can never overwrite the original assessor. There is no score/level/band column anywhere in this table by design — `operational_constraints` is a plain `text[]` over a fixed vocabulary (validated in the service layer), the same pattern as `reports.flags`, never a numeric field.

### `work_orders`
- **Purpose:** The actual field work MEO/MDRRMO staff must do to resolve a ticket — a ticket may have several work orders. Carries `title`, an internal `notes` progress trail, `assigned_office`/`assigned_admin_id`, its own `work_order_status` (`pending`/`in_progress`/`completed`/`cancelled` — deliberately not `ticket_status`, same reasoning `office_reassignments` doesn't reuse it), `due_date`, and `completed_at`. Advancing or completing a work order never mutates the linked ticket's own `status` — no safe automatic coupling rule exists yet (see [`project-status.md`](project-status.md)).
- **Reads:** `/admin/work-orders` (list, office-scoped), the Work Orders panel on admin Ticket Detail.
- **Writes:** `WorkOrdersService.create`/`update`/`setStatus` (`api/src/admin/work-orders.service.ts`), each logging an `admin_audit_events` row.
- **Expected empty?** Normal to be empty until the first work order is created — not part of every ticket's lifecycle.
- **Ownership:** Application (Drizzle) — no geometry column.
- **Note:** `notes` is internal-only and must never appear in any `api/src/citizens/*` response or the citizen tracking timeline. `assigned_admin_id`/`created_by_admin_id` are FK-less integers, same cross-table reasoning as `status_history.admin_id`/`office_reassignments.admin_id`.

### `work_order_status_history`
- **Purpose:** Append-only status timeline for work orders — what `status_history` is to tickets. `work_orders` stores only the *current* status, so before this table a `pending` → `in_progress` transition left no trace and "how many work orders were pending on date X" was unanswerable (`cancelled` never sets `completed_at`, so even a `created_at`/`completed_at` approximation was wrong). Carries `work_order_id`, the `work_order_status` value, and a write-time `admin_id`/`admin_name` snapshot.
- **Reads:** `DashboardService.getPendingWorkOrderTrend` — the Pending Work Orders KPI sparkline on `/admin`.
- **Writes:** `WorkOrdersService.create` (one origin row, in the same transaction as the INSERT) and `WorkOrdersService.setStatus` (one row per transition, in the same transaction as the UPDATE). Never written anywhere else.
- **Expected empty?** Only before the first work order exists. The migration seeds one origin row per pre-existing work order at its `created_at` with `pending`.
- **Ownership:** Application (Drizzle) — no geometry column.
- **Honesty caveat:** History exists only from migration `0027` forward. Real transitions that happened *before* the migration are unrecoverable and are deliberately not invented — the seeded origin rows only give each pre-existing work order a defined starting point. Early dates in the trend can therefore read high, since a work order completed before the migration still resolves to its seeded `pending` origin. This is documented rather than smoothed over because the alternative is a chart that silently lies about the past.
- **Relation to `admin_audit_events`:** Separate on purpose. The audit log is System-Administrator-only and keyed on *actor*; this table is a metric source keyed on the work order. Deriving the trend from the audit log would couple a dashboard chart to an access-restricted oversight trail.

### `notifications`
- **Purpose:** One row per notification, targeted either at a specific `recipient_id` (an admin or citizen, per `recipient_type`) or at an entire `recipient_office` (admin-only, read by every admin in that office — no per-admin fan-out rows). No FK on `recipient_id` since it points to one of two different tables depending on `recipient_type`.
- **Reads:** Notification bell/list UI (citizen and admin), read by both a specific-recipient query and an office-wide query.
- **Writes:** `NotificationsService.create`/`createInTx`, fired from report submission, moderation, status changes, etc.
- **Expected empty?** Only if nothing notification-worthy has happened yet.
- **Ownership:** Application (Drizzle).
- **Cleanup:** `POST /cron/cleanup-notifications` prunes *read* notifications older than 30 days (unread ones are kept regardless of age until actually read) — called daily by `.github/workflows/cron.yml` (Production Hardening), in addition to being callable on-demand.

### `admin_audit_events`
See §E (System/admin security tables) — kept there since it's specifically part of the admin-security/oversight story, alongside `admins`' own security columns.

### `citizen_audit_events`
- **Purpose:** Append-only trail for the Account & Security page's sensitive actions (OAuth provider linked/unlinked, password set/changed, rejected link conflicts due to email collision). Never updated or deleted, only inserted.
- **Reads:** Citizen's own Account & Security activity view.
- **Writes:** `AccountService`/`ResendEmailService`/OAuth linking flow, on every sensitive action.
- **Expected empty?** Yes for a citizen who has never touched Account & Security beyond initial signup.
- **Ownership:** Application (Drizzle).
- **Relation to `admin_audit_events`:** Intentionally separate — different actor types, different event vocabularies, different audiences (this one is citizen-self-service; the admin one is System-Administrator-only). See §G below for the full cross-table rationale.

### `admin_saved_views`
- **Purpose:** Personal filter presets for an admin table's view-tab strip — the tabs that appear after the built-in ones. Two surfaces use it: the Ticket Queue ("All active", "Disputed", "MEO", "MDRRMO"; the "High urgency" tab was removed in manuscript revision Phase 1, step 4) and Flagged Reports ("All flagged", "Pending review", "Quarantined", "Dismissed", "Duplicates"). One row per saved preset per admin per surface.
- **Reads:** `SavedViewsService.list`, called by `app/admin/tickets/page.tsx` and `app/admin/flagged/page.tsx` on first paint and by `GET /admin/saved-views?surface=`. Both call sites let the fetch fail to an empty list — a saved view is a convenience, never load-bearing for the table.
- **Writes:** `SavedViewsService.create` ("Save this view" in either view-tab strip) and `.remove` (the × on a saved tab). Re-saving an existing name UPDATEs that row rather than inserting a near-duplicate — enforced by the `(admin_id, surface, name)` unique index.
- **Expected empty?** Yes. Saved views are opt-in; a fresh install and most admins will have none, and the queue renders its built-in tabs regardless.
- **Ownership:** Application (Drizzle).
- **Scoping:** Strictly personal. `admin_id` is the only read/write key and is the authorization boundary — there is no office-wide or shared preset, and `remove` matches on `(id, admin_id)` so one admin can never delete another's. Unlike `status_history.admin_id` and `admin_audit_events.actor_admin_id`, which deliberately keep an unreferenced id so history survives the actor, this table uses a real FK with `ON DELETE CASCADE`: a deleted admin's private bookmarks have no historical value.
- **Why `query` is a string, not columns:** It stores the serialized querystring (e.g. `status=active&sort=op_priority_desc`), so adding a new filter never requires a migration here. It is re-parsed through the same URL parsing the address bar uses and then through the surface's own server-side parser — `TicketsService.parseTicketQuery` or `ModerationService.parseModerationQuery` — which means a stored or hand-edited `office=` can never widen scope past `resolveOfficeScope`. A saved view is a bookmark, never a grant; adding a surface changed which parser replays the string, not whether one does.
- **`surface` (added in `0029`):** `'tickets' | 'flagged'`, CHECK-constrained, defaulting to `'tickets'` — which is also what backfilled every pre-existing row, since the Ticket Queue was the only surface able to write one before the column existed. It keeps the two strips disjoint: without it a queue preset would replay `urgency=High` against Flagged Reports, whose parser has no such filter, and silently resolve to no filters at all. A request that omits `surface` still means `'tickets'` (`parseSavedViewSurface`), so the Ticket Queue's existing calls were not changed.
- **`0034` rewrite (manuscript revision Phase 1, step 4):** `api/drizzle/0034_saved_views_retire_hazard_urgency.sql` rewrote Ticket Queue presets off the retired Hazard Urgency keys — `sort=priority_desc|priority_asc` became `sort=op_priority_desc|op_priority_asc`, and any `urgency=` parameter was removed. Names were left as each admin typed them (a preset named "High urgency" keeps its name but now shows everything its remaining filters match). Flagged presets were not touched. Re-runnable; `0034_saved_views_retire_hazard_urgency.check.sql` counts what is left to rewrite and must return all zeros afterwards. Run with `pnpm --prefix api migrate:saved-views-retire-hazard-urgency`.
- **`0040` rewrite (manuscript revision Phase 3, step 3b):** `pnpm --prefix api migrate:evidence-flags` rewrites Flagged Reports presets off the retired flag codes, in the same transaction as the reports update: `flag=STALE_PHOTO` becomes `flag=STALE_EVIDENCE`, and a `flag=NO_EXIF` filter is removed (no new code means "photo without GPS"). The query is parsed with `URLSearchParams`, as in 0035; untouched rows keep their encoding. `saved_views_old_codes` in `0040_evidence_flags.check.sql` must be 0 afterwards.
- **Caps:** 12 views per admin **per surface**, name ≤ 40 chars, query ≤ 500 chars (`SavedViewsService`). Per surface rather than per admin, so a full Ticket Queue strip cannot block saving anything on Flagged Reports.
- **Counts:** Built-in tabs carry server-computed counts (`TicketsService.getViewCounts` on `GET /admin/tickets`; `GET /admin/moderation/stats` for Flagged Reports, whose "All flagged" tab is the sum of the four states). Saved views deliberately carry **no** count — counting an arbitrary stored filter would mean one aggregate query per preset on every page load.

## B. GIS/PostGIS tables and views

### `barangays`
- **Purpose:** The 29 official PSGC/OCHA-sourced barangay polygons for the target municipality (Porac by default — see `MUNICIPALITY` config). This is where barangay *identity* always comes from — never from `city_boundary_osm` (see below).
- **Reads:** `BarangayService.findBarangayForPoint` (primary `ST_Contains` check + nearest-`<->` fallback snap), admin map choropleth, ticket/report barangay display.
- **Writes:** `pnpm --prefix api import:barangays` (`api/scripts/seed/import-barangays.ts`) — update-by-name, not truncate-and-reinsert, because `tickets.barangay_id` has a real FK to this table.
- **Expected empty?** No — required for the app to function at all (barangay resolution is mandatory for every report). Empty means `import:barangays` was never run.
- **Ownership:** Application, raw-PG-only (not in `schema.ts` — see its header comment). PostGIS provides the `geometry`/`GIST` machinery, but the table itself is app-owned data.
- **Related:** `barangays_gadm_old` — the previous GADM-sourced table, kept for rollback/reference only, never queried by app code. Never delete without reading `docs/migration-log-gadm-to-psgc.md` and `PLAN.md` §4.1 first.

### `dem_points`
- **Purpose:** SRTM 30m digital elevation model, sampled into `(lon, lat, elevation_m)` point rows, one per DEM cell inside a barangay polygon.
- **Reads:** Barangay Insights' per-barangay elevation range (display only). The nearest-neighbor (`<->`) elevation lookup on report submission was removed in manuscript revision Phase 1, step 7a. Also the one-time `elev_min`/`elev_max` computation feeding `config` (see §C).
- **Writes:** `pnpm --prefix api seed:dem` (`api/scripts/seed/seed-dem.ts`) — truncate-and-reinsert (idempotent), from `scripts/gis/raw/porac_srtm30m.tif`.
- **Expected empty?** No — required for elevation-based urgency scoring to work at all. Empty means `seed:dem` was never run.
- **Ownership:** Application, raw-PG-only.

### `city_boundary_osm`
- **Purpose:** A single outer-envelope polygon for the whole municipality. Used **only** as a looser second containment check — when a report's coordinates fall outside every barangay polygon (a known gap in the barangay dataset's edges), the app checks whether the point is at least inside the *city as a whole*; if so, it snaps to the nearest barangay by distance instead of rejecting the report outright. Barangay identity is never derived from this table.
- **Reads:** `BarangayService.findBarangayForPoint` (`api/src/domain/barangay.service.ts`), fallback branch only.
- **Writes:** `pnpm --prefix api import:city-boundary` (`api/scripts/seed/import-city-boundary.ts`) — truncate-and-reinsert (idempotent; no FK ever references this table's `id`, unlike `barangays`).
- **Data source:** `MUNICIPALITY.osmBoundaryFile` (default `public/assets/gis/porac_osm_boundary.json`). Despite the "OSM" name, this file is **not** an independent OpenStreetMap import for Porac — it's generated by `pnpm gis:generate-boundary` (`scripts/gis/generate-porac-boundary.ts`), which dissolves the 29 already-imported PSGC barangay polygons into one seamless union via Turf.js. That's deliberately more consistent for this fallback check than a separately-sourced OSM extract would be (no risk of the two datasets disagreeing at the edges). The name is a holdover from the original design (PLAN.md describes a real OSM relation import, done manually, for an earlier target municipality before the PSGC-dissolve approach replaced it).
- **Expected empty?** **This was the actionable gap this document's companion fix addressed.** The table's *creation* (`migrate:city-boundary`) was always a documented setup step, but no committed script ever populated it — so a fresh database following only the old documented steps had this table permanently empty, silently making the fallback branch always reject (any point missing every barangay polygon would be treated as outside the city, with no error or warning anywhere). `import:city-boundary` now exists specifically to fix this; run it (idempotent, safe to re-run) and `verify:city-boundary` to confirm. If it's still empty after running that script, that's a real problem worth investigating, not a normal state.
- **Ownership:** Application, raw-PG-only.

### `geometry_columns`
- **Purpose:** PostGIS system catalog view, auto-populated by `CREATE EXTENSION postgis`. Lists every `geometry`-typed column in the database for tooling introspection (QGIS, `ogr2ogr`, spatial-reference lookups). The app never queries it.
- **Reads/writes:** None by app code. Populated automatically whenever a `geometry` column is created/dropped.
- **Expected empty?** No — it should list an entry for every real spatial column this app has (`barangays.geom`, `dem_points.geom`, `tickets.geom`, `reports.geom`/`pin_geom`/`exif_geom`, `city_boundary_osm.geom`, `rate_limit_events.geom`). If it's empty, PostGIS itself is broken, not this app.
- **Ownership:** PostGIS extension / system metadata.
- **Never manually delete.**

### `geography_columns`
- **Purpose:** Same as `geometry_columns`, but for `geography`-typed columns.
- **Expected empty? Yes, and this is normal** — this app never declares a column as `geography`; every spatial column is `geometry`. `geography` only ever appears as an inline cast in query text (e.g. `geom::geography` in `barangay.service.ts`/`ratelimit.service.ts`, used for accurate meter-based `ST_Distance`/`ST_DWithin` calculations). A cast is not a column declaration, so it never populates this view. An empty `geography_columns` is expected and correct — it is not evidence of missing setup.
- **Ownership:** PostGIS extension / system metadata.
- **Never manually delete.**

## C. Configuration and scoring tables

### `config`
- **Purpose:** A small key-value cache table serving two related-but-distinct concerns:
  - **`elev_min` / `elev_max`** — no longer read since manuscript revision Phase 1, step 7a (`AppConfigService` was deleted); kept until Phase 8. Fixed, DEM-derived elevation bounds used to normalize the urgency formula's elevation factor. Computed once from `dem_points` at seed/migration time (`drizzle/0007_config.sql`), read by `AppConfigService.getElevationBounds()`. **Never recomputed live** — these are static application configuration, not live state.
  - **`rain_1h_mm`** — no longer written since manuscript revision Phase 1, step 7a (`WeatherService` was deleted); the existing row is kept as a stale value until Phase 8 cleans it up. Previously a live OpenWeatherMap cache, ~10-minute TTL, read/written by `WeatherService.getCurrentRain1hMm()`. This *is* live runtime telemetry, refreshed on-demand by any admin dashboard/ticket-queue/map load (which recomputes urgency) and by the manual `POST /cron/recompute-weather` trigger. On fetch failure it falls back to the stale cached value (or `0mm` if there's never been one) rather than erroring, so a weather-API outage doesn't 500 every admin route.
- **Reads:** `AppConfigService` (elevation bounds), `WeatherService` (rain cache).
- **Writes:** `WeatherService` (rain cache, every ~10 min on read-triggered refresh); `elev_min`/`elev_max` are written exactly once, at seed time, by migration SQL — no runtime code writes them.
- **Expected empty?** No — `elev_min`/`elev_max` are load-bearing for every urgency computation; a missing row here would corrupt scoring. Empty means `seed:dem` + `migrate:config` were never run (missing setup), not evidence this feature is unused.
- **Ownership:** Application, raw-PG-only.
- **Design note (future consideration only — not changed by this pass):** This table currently mixes a static-constant role and a live-telemetry-cache role under one shape. That's fine at its current size (3 rows) but is a candidate for eventually splitting into e.g. `elevation_config` (static) and `weather_cache` (live, TTL'd) if the number of config keys ever grows enough that the dual purpose becomes confusing. Not attempted in this pass — see the database audit for the full rationale.

## D. Authentication/security tables

### `citizen_identities`
- **Purpose:** One row per (citizen, external OAuth provider) link. Google is the only provider the app currently issues (Facebook enum value retained only because Postgres can't cheaply drop an enum value — no live code path uses it). A citizen can hold at most one identity per provider; a given provider account can only ever back one citizen.
- **Reads:** OAuth login (identity lookup), Account & Security page (linked-provider list).
- **Writes:** OAuth callback (link/first-login), Account & Security unlink action.
- **Expected empty?** Normal to be empty if no citizen has ever used Google login — password-based signup never touches this table.
- **Ownership:** Application (Drizzle).

### `password_reset_tokens`
- **Purpose:** One row per issued citizen password-reset link. Only a SHA-256 hash of the actual token is stored (the raw token exists only in the emailed URL and the requesting citizen's browser) — `token_hash` is the lookup key precisely because it's useless to an attacker who reads the database. `used_at` makes it single-use; `expires_at` makes it short-lived.
- **Reads:** `PasswordResetService`, on the reset-link-click flow.
- **Writes:** `POST /citizens/forgot-password` (insert), reset completion (`used_at`).
- **Expected empty?** Normal to be near-empty most of the time — tokens are short-lived and single-use.
- **Ownership:** Application (Drizzle).
- **Cleanup:** `POST /cron/cleanup-password-reset-tokens` prunes expired/used tokens — called daily by `.github/workflows/cron.yml` (Production Hardening), in addition to being callable on-demand.

### `rate_limit_events`
- **Purpose:** Postgres-backed rate limiter for **report submission only**. Three independent checks: per-citizen hourly cap (primary), per-citizen spatial cap (3 within 25m/24h — catches repeat submissions near the same spot), per-IP hourly backstop (secondary, catches one IP spinning up many accounts).
- **Reads/writes:** `RateLimitService.checkRateLimit`/`recordRateLimitEvent` — the write happens inside the same transaction as the ticket/report insert, so only successful submissions count against the limit.
- **Expected empty?** Normal on a fresh DB before any report has been submitted; grows with every submission attempt otherwise.
- **Ownership:** Application, raw-PG-only (has a `geom` column, `NOT NULL`).
- **Cleanup:** `POST /cron/cleanup-rate-limit-events` (`RateLimitService.cleanupOldEvents`) prunes rows older than 30 days — called daily by `.github/workflows/cron.yml`. 30 days is a wide safety margin over the longest window this table's checks ever query (24 hours, the per-citizen spatial check), so it can never delete a row a live rate-limit decision still depends on.

### `password_reset_rate_limit_events`
- **Purpose:** A **separate** rate limiter, specifically for the forgot-password endpoint (`POST /citizens/forgot-password`) — per-email (primary, 3/hour) and per-IP (secondary backstop, 10/hour). Records a row for *every* attempt, including ones for emails that don't exist, so enumeration probing can't dodge the limit by trying many addresses.
- **Reads/writes:** `RateLimitService.checkPasswordResetRateLimit`/`recordPasswordResetAttempt`.
- **Why separate from `rate_limit_events`:** That table's `geom` column is `NOT NULL` — a forgot-password request has no location. Forcing this event into the geo table would mean either fake placeholder geometry (bad data) or relaxing that table's `NOT NULL` constraint (weakening its real use case). The separation is a direct consequence of a real schema constraint, not arbitrary duplication — **do not merge these two tables.**
- **Expected empty?** Normal on a fresh DB before any forgot-password request has been made.
- **Ownership:** Application, raw-PG-only (no geometry).
- **Cleanup:** Same `POST /cron/cleanup-rate-limit-events` call prunes this table too (30-day cutoff) — both tables' checks only ever query 1-hour windows, so the same wide margin applies here even more comfortably than for `rate_limit_events` above.

### `admin_login_rate_limit_events`
- **Purpose:** Per-account failed-login throttling for admin login (R1) — keyed on the normalized account email only, never IP (an IP-based total-login limit would break the E2E suite, which authenticates from one IP nearly 200 times per run). 10 failures within 15 minutes throttles further attempts against that email. Only failed attempts are recorded; a successful login deletes that email's rows outright rather than waiting for them to age out — the one table in this app whose rate limiting actively resets rather than only expiring.
- **Reads/writes:** `RateLimitService.checkAdminLoginRateLimit`/`recordAdminLoginFailure`/`resetAdminLoginFailures`, called from `AuthService.adminLogin`. A failure is recorded for every rejection reason — nonexistent email, deactivated admin, wrong password — never only for real/active accounts, so the throttle itself can't become an enumeration side-channel (mirrors `recordPasswordResetAttempt`'s identical choice).
- **Why separate from `password_reset_rate_limit_events`** even though the column shape is identical: that table is a different security domain already in active use by citizen forgot-password requests (its own email/IP limits). Mixing admin-login-failure rows into it would corrupt those counts and conflate two unrelated actor types — the same category of mistake `rate_limit_events`/`password_reset_rate_limit_events` staying separate already guards against, just one level over.
- **Expected empty?** Normal on a fresh DB, and in steady state — it only holds rows for accounts currently mid-throttle or between failures and their next success.
- **Ownership:** Application, raw-PG-only style access (Drizzle-declared for schema documentation, but always queried via the raw `Sql` client, same as `password_reset_rate_limit_events`).
- **Cleanup:** Same `POST /cron/cleanup-rate-limit-events` call prunes this table too (30-day cutoff) — its own check only ever queries a 15-minute window, so the margin here is wider still than either sibling table's.

### `citizen_login_rate_limit_events`
- **Purpose:** Per-account failed-login throttling for citizen login (hardening item 3) — identical shape and reasoning to `admin_login_rate_limit_events`: keyed on normalized email only, never IP (the E2E suite's `signupCitizen()` fixtures log in from one shared local IP across specs). 10 failures within 15 minutes throttles further attempts against that email; a successful login deletes that email's rows outright.
- **Reads/writes:** `RateLimitService.checkCitizenLoginRateLimit`/`recordCitizenLoginFailure`/`resetCitizenLoginFailures`, called from `AuthService.citizenLogin`. A failure is recorded for every rejection reason — nonexistent citizen, OAuth-only account (null password hash), wrong password — never only for real accounts.
- **Why separate from `admin_login_rate_limit_events`** even though the column shape is identical: different security domain (citizen vs. admin accounts), same reasoning as every other pair in this section — see §G.
- **Expected empty?** Normal on a fresh DB, and in steady state — only holds rows for accounts currently mid-throttle or between failures and their next success.
- **Ownership:** Application, raw-PG-only style access (Drizzle-declared for schema documentation, always queried via the raw `Sql` client).
- **Cleanup:** Same `POST /cron/cleanup-rate-limit-events` call prunes this table too (30-day cutoff).

### `citizen_signup_rate_limit_events`
- **Purpose:** Account-creation-spam throttling for citizen signup (hardening item 3) — IP-only, no email column, since signup abuse is bounded by volume of *distinct* new accounts from one source rather than repeat attempts against one target address (duplicate email is already rejected by the existing `citizens.email` conflict check, unrelated to this table). 20 signups within 1 hour per IP — the same value as `rate_limit_events`' IP backstop, sized against the E2E suite's actual measured signup volume (~17 disposable citizen accounts per full run) rather than picked arbitrarily.
- **Reads/writes:** `RateLimitService.checkCitizenSignupRateLimit`/`recordCitizenSignupAttempt`, called from `AuthService.citizenSignup`. An attempt is recorded for every request that clears the rate-limit check itself, regardless of whether it goes on to hit the duplicate-email conflict or succeed.
- **Expected empty?** Normal on a fresh DB before any signup has been attempted.
- **Ownership:** Application, raw-PG-only style access (Drizzle-declared for schema documentation, always queried via the raw `Sql` client).
- **Cleanup:** Same `POST /cron/cleanup-rate-limit-events` call prunes this table too (30-day cutoff) — its own check only ever queries a 1-hour window.

### `verifications`
- **Purpose:** **Not email/account verification.** This is planned/future schema for a citizen "upvote a ticket" signal — one row per (ticket, citizen) attesting "I also see this problem," intended as a possible future input to the urgency formula's Cluster Density factor (per `PLAN.md`'s explicit "keep and formalize" note). The feature that would write to this table has never been built.
- **Reads/writes:** None — no service, controller, or test touches it. It exists in `schema.ts` only.
- **Expected empty?** Yes, always, until this feature is actually built. This is not evidence of dead/leftover-and-forgotten schema — it's a deliberate, documented decision (see `PLAN.md`) to keep the table rather than build-then-delete-then-rebuild later.
- **Naming caveat:** `citizen_id` on this table is typed `text`, not the `integer references citizens(id)` every other citizen-referencing column uses — it predates the `citizens` table (added two migrations later). If this table is ever wired up, that column needs a type migration first.
- **Ownership:** Application (Drizzle).
- **Do not delete** without first re-reading `PLAN.md`'s "Keep and formalize: citizen verifications" note and confirming the product decision has actually changed.

## E. System/admin security tables

### `admin_audit_events`
- **Purpose:** Append-only trail for administrative actions — account create/role change/deactivate/reactivate, ticket status/reassignment/referral/rejection, report moderation, work order create/update/status change, and admin login/failed-login (`admin_login`/`admin_login_failed`). System-Administrator-visible only. `actor_*` columns are a snapshot at write time (name/role/office can change later on the `admins` row itself), so history reads correctly even after the actor is edited. **`actor_account_type`** (`admin_account_type`, `NOT NULL`; manuscript revision Phase 2, step 2e, migration `0039`) is the Appendix H actor account type; keeping it **beside the historical `actor_role`** is an implementation extension. `0039` filled it for every existing row from `actor_role` (`officer`/`supervisor`/`focal` → `PERSONNEL`, `system_admin` → `SYSTEM_ADMIN`) and **never touches `actor_role`**. New events set `actor_account_type` from the actor's account type and `actor_role` from the actor's stored `admins.role` mirror (a subquery in the INSERT, since the session has no role). The insert trigger `admin_audit_events_fill_actor_account_type` fills `actor_account_type` from `actor_role` only when an insert leaves it NULL, so older code keeps writing audit events; both it and `actor_role` go in Phase 8. The Activity Log labels every actor, old or new, from `actor_role`: Personnel / Focal Personnel / System Administrator. `action_type`/`target_type` are plain `text`, not enums — a new action type is a pure application-code change, no migration required (e.g. `ticket_referral_noted`'s `metadata: { agency, note }`, Phase 3; `ticket_rejected`'s `metadata: { from, to: 'Rejected', reason }`, Phase 4; the staff grouping actions of manuscript revision Phase 3, step 3d: `ticket_merged` on the survivor ticket with `{ mergedTicketId, movedReportIds, reason }`, `report_removed_from_ticket` on the report with `{ fromTicketId, newTicketId, reason }`, `report_regrouped` on the report with `{ fromTicketId, toTicketId, reason }`; the staff corrections of step 3e: `ticket_category_corrected` with `{ field: 'category', oldValue, newValue, reason, officeChanged, fromOffice, toOffice }` and `ticket_location_corrected` with `{ field: 'location', oldLat, oldLng, oldBarangay, newLat, newLng, newBarangay, distanceM, reason }`, both on the ticket — the correction history the Ticket Detail timeline reads; no column on `tickets` keeps the previous value; Focal's severity screening of step 3f: `report_severity_screened` on the report with `{ oldStatus, newStatus, remarks }`, one per screening — `report_screened`, the old general screening action, stays as history and is never written again). Read back per-ticket on the Ticket Detail page as a **historical** referral list — never treated as live "currently pending referral" state, since reconstructing that from an event log would need a resolution-event convention this table doesn't have. **The `ticket_rejected` reason lives only in this table's `metadata` column — `tickets` has no `rejection_reason` column and none was added for this.** Deliberate: audit metadata may document an action without becoming authoritative live ticket state (same reasoning as the referral agency/note above); a citizen sees the reason only inside the rejection notification/email text, never as a queryable ticket field.
- **Reads:** Activity Log page (`GET /admin/activity-log`, System Admin only).
- **Writes:** `AdminAuditService.logInTx`/`logInPgTx`, called from every admin-management/ticket/moderation write path that changes state — the write is transactional with the state change itself (a failed audit insert rolls back the whole action; this trail is treated as load-bearing, not best-effort). **Exception:** `admin_login`/`admin_login_failed` are written via `AdminAuditService.logBestEffort` from `AuthService.adminLogin`, outside any transaction and best-effort (errors are caught and logged, never rethrown) — login has no accompanying state-change transaction to join, and a broken audit insert must never block a legitimate login. A failed login against a nonexistent email is not audited at all: `actor_admin_id` is `NOT NULL` and there is no admin row to attribute one to.
- **Expected empty?** No once any admin action has been taken; normal to be empty on a completely fresh DB.
- **Ownership:** Application (Drizzle).
- **Relation to `citizen_audit_events`:** Intentionally separate — see §G.

### Admin password/session security columns (on `admins`)
- **`password_changed_at`** — set/refreshed whenever `password_hash` changes (own change or a System Admin reset).
- **`session_valid_after`** — bumped to `now()` on the same two events; `SessionService.verifyAdminSession` rejects any JWT whose `iat` predates this value — the one place a stateless JWT admin session can actually be invalidated server-side after a credential change. `null` means "never invalidated, accept any `iat`" (the default for every existing/new admin).
- **Mirrors:** `citizens.password_changed_at`/`session_valid_after`, same mechanism, same reasoning, applied to the other principal type.

### Admin activation/deactivation status (on `admins`)
- **`is_active`** — `false` blocks login (`AuthService.adminLogin`) and invalidates every existing session immediately (deactivation bumps `session_valid_after` in the same write, so an already-issued JWT dies within the request cycle, not just at its 8h expiry). Reactivation only flips this back; the admin logs in fresh with their existing password.
- **Lockout protection:** `AdminsService.setActive` blocks deactivating the last **active** `system_admin` (mirrors the equivalent role-demotion lockout) — the system can never end up with zero admins able to manage other admins.
- **No `citizens.is_active` equivalent** — intentional, not missing work. Citizens are self-service accounts; there is no "deactivate a staff account" workflow in the product for them.

## F. Naming/terminology callouts

- **`verifications` ≠ email/account verification.** See §D — it's a planned ticket-upvote feature, unrelated to identity verification.
- **`urgency_score`/`urgency_band` ≠ `priority_score`/`urgency_level` ≠ `priority_index`.** All live on `tickets`, all sound similar, and are genuinely different things — see CLAUDE.md's "Terminology: Severity vs. Urgency vs. Priority" section for the authoritative explanation. Not repeated in full here to avoid the two documents drifting out of sync; when scoring changes, update CLAUDE.md first.
- **Hazard Urgency / Operational Priority / Operational Assessment are three distinct decision-support layers**, not synonyms for "priority." Hazard Urgency (`priority_score`/`urgency_level`) and Operational Priority (`priority_index`) are both system-generated and both live on `tickets` — see the bullet above. Operational Assessment (`operational_assessments`, five-role Batch 3) is the third, human-entered layer and is structurally incapable of being a score: no numeric/level/band column exists anywhere in that table.
- **`admins.role` (`admin_role` enum) has four values**, not three: `officer`, `supervisor`, `system_admin`, `focal` (five-role Batch 1). `focal` always carries `office = 'MDRRMO'` (organizational, not operational) — see `api/src/common/authz/admin-scope.ts`'s `isOperationalStaff`, which excludes `focal` despite that office value.

## G. Cross-table design notes

- **`rate_limit_events` vs. `password_reset_rate_limit_events`** — keep separate; driven by a real `NOT NULL geom` constraint difference, not duplication. See §D.
- **`password_reset_rate_limit_events` vs. `admin_login_rate_limit_events` vs. `citizen_login_rate_limit_events`** — identical or near-identical column shapes, kept separate anyway: different security domains (citizen forgot-password, admin login, citizen login) with independent limits and independent actor types. Merging any of them would let one domain's attempts count against another's threshold. See §D.
- **`citizen_signup_rate_limit_events`** — IP-only, no email column, unlike its login/reset/admin-login siblings; not a shape mismatch to reconcile, a deliberate consequence of signup's different threat model (volume from a source, not repeat attempts against a target). See §D.
- **`admin_audit_events` vs. `citizen_audit_events`** — keep separate; different actor types, different event vocabularies, different audiences (System-Administrator-only vs. citizen-self-service), each independently documenting the same "actor snapshot at write time" pattern for its own reasons.
- **`admins`' security/session/status columns vs. `citizens`' security/session columns** — parallel by design, not accidentally duplicated; each principal type owns its own copy so one type's auth model can evolve (e.g. admin deactivation) without silently changing the other's.
- **`config` vs. weather/telemetry state** — currently share one table; see §C's design note. Not split in this pass.
- **`city_boundary_osm` vs. static GeoJSON assets** — no real overlap. The frontend map's boundary overlay and this table's fallback-containment check happen to read from the same underlying generated file (`porac_osm_boundary.json`), but for different reasons (rendering vs. spatial query) and through different mechanisms (a browser `fetch` vs. a database `ST_Contains`) — this is reuse of one source of truth, not confusing overlap.
